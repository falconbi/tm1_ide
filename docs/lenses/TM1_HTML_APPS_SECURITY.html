HTML apps on TM1:
the security layer you now own

PAW handled the browser. When the screen is HTML you author — or an AI writes — you inherit that layer. Most TM1 developers have never had to know what it does. This is the layer, in plain terms, with the five decisions it makes and the eight checks to run before anything reaches a user.

01

The shift

For most of its life, building on TM1 meant rules, feeders, dimensions, processes and a cube view. The browser was somebody else’s problem.

Planning Analytics Workspace owns that layer. It authenticates users, keeps sessions, blocks cross-site request forgery, renders data safely, sets content security policy, terminates TLS and patches its own framework. None of it is free — it is inside the licence. It is also invisible, so a TM1 developer never has to learn it.

An HTML app changes one thing: the page is untrusted content. PAW composes screens inside a runtime it controls. When the screen itself is arbitrary HTML, the platform cannot vouch for it, so whoever ships it inherits the layer.

“Untrusted” does not mean “malicious”. It means the platform has no way to know what the page will do. The page is text sent to the browser; the browser renders it and runs its JavaScript. If a person wrote it, or an AI wrote it and a person reviewed it, the runtime still cannot read it and decide it is safe. So it must be treated as content, not as code the platform trusts.

AI made the build cheap. It did not make the page trustworthy.

Principle. A page can be authored freely only if the platform stops trusting it.

02

The web layer, in plain terms

Before the security, the mechanics. Six words carry most of this article, and none of them are TM1 words.

WordWhat it meansClosest TM1 idea
BrowserA program on the user’s machine that asks for pages and draws them. Chrome, Edge, Safari.Architect — but the user can change anything inside it
ServerA program on a machine somewhere, listening for requests, sending answers.The TM1 server — though here it is your small web app
Request“Give me this page”, or “save this number”. A method, a URL, some headers, sometimes a body.A REST call to TM1
ResponseThe answer: a status code, headers, and a body (usually HTML or JSON).What the REST call returns
CookieA small piece of text the server asks the browser to store and send back on later requests.A claim ticket — not a login
SessionThe server’s own record that a user signed in. The cookie is only the key to it.A client connection in }ClientProperties

The important structural fact: the browser is a separate computer that you do not control. It will do what the user, the page, or a browser extension tells it to. Everything in it — the HTML, the JavaScript, hidden fields, a “current user” variable — can be changed before it comes back.

That is why every decision that matters has to be made on the server. The page can ask; only the server can decide.

Authentication and authorisation are different questions. Authentication asks “who is this?” — usually answered once, by TM1, at sign-in. Authorisation asks “what may they see or change?” — answered on every request, also by TM1. Most security mistakes come from answering the first and forgetting the second.

HTTP has no memory. Each request arrives as a stranger; the server remembers nothing between them. Identity has to be carried, and the only thing the browser carries automatically is the cookie. So the cookie is a ticket, and the session is the coat check where the server looks up what the ticket means.

03

The threat model, in TM1 terms

Three failures explain most of the risk, and each has a TM1-shaped version.

A service account is not “the app”

If the web layer talks to TM1 as one shared login, every user is that login. Region security, cost-centre security and version locks stop applying, because TM1 sees a single powerful user. The app can still display a filter; that is a UI, not a right.

Hiding a button is not a permission

The same as hiding a cube in Architect. If the server performs the action when asked, the button was never the control. A user can post the request without the button, and a script can do it in a loop.

A session cookie is a bearer token

Whoever holds it is the user until it expires. It is not a password and it is not proof of anything on its own; it is a ticket, and the server trusts whoever presents it. That is why the cookie is protected in transit, hidden from JavaScript, and given a short life.

The browser is someone else’s computer

HTML, JavaScript, hidden fields and “current user” variables can all be changed before they come back. Anything the page says about who it is, what it may do, or which server to use is a claim, not a fact.

Rule. The server never accepts an identity, a server name or a permission from the page.

04

The five layers

This is the whole model. Each layer answers one question, and each fails in its own way.

QuestionLayerControlTypical failure
Can anyone on the path read or change this?TransportTLS from a trusted CA, HTTPS redirect, HSTS, Secure cookiesSecure decided by a config flag instead of the request
Who is this?Identityper-user TM1 login, random session id, HttpOnly, SameSiteone shared service account
What may they see or change?AuthorisationTM1 security on every read and direct write; declared write cubes and processeschecks made in the UI
Is this page allowed to ask?Isolationsandboxed frame, opaque origin, connect-src 'none', message bridgeallow-same-origin
Did this request come from my app?Provenanceserver-side Origin check, __Host- cookies, host-only scoperelying on SameSite alone

Transport — is the connection private and genuine?

TLS encrypts the conversation between the browser and whatever accepts the connection, and proves the server is the one the user typed. On an internal network it is still required: credentials and session cookies are the payload, and an internal LAN is not a trust boundary.

The two details that matter more than the certificate:

  • the Secure flag must follow the request the browser actually made, not “is this process configured for TLS” — behind a reverse proxy those are different questions;
  • HTTP must redirect to HTTPS, and the browser must be told (HSTS), or the first request, including the sign-in form, can still travel in clear text.

Identity — who is it?

Every user signs in as themselves, against TM1. The app keeps one TM1 session per user and gives the browser a random session id.

The TM1 side of that — native, LDAP, CAM, Windows integrated, v12 tokens, OpenID Connect and PAW — is covered in How signing in to TM1 works. This article is about what the browser layer must do with the result.

  • the password is checked once, with TM1, and never stored;
  • the cookie contains only an opaque id — not the username, groups or a token;
  • HttpOnly means page scripts cannot read it;
  • SameSite=Strict means other sites cannot make the browser send it.

Authorisation — what may they do?

TM1 decides on every read and every direct cell write, as the signed-in user. The app’s job is to ask, not to judge:

  • reads go through TM1, so cell security applies;
  • writes are checked against the cubes the saved screen declares, and TM1 still refuses calculated cells and cells the user may not change;
  • process runs are checked against the process list the saved screen declares, with parameter types validated;
  • opening a screen is checked against a TM1 group.

One honest qualification. A running TI process is not limited by the caller’s cell security. Any action process must check the caller itself and report why it refused. “TM1 security applies” is true for reads and direct writes; it does not automatically follow a process into its work.

Isolation — is this page allowed to ask?

The authored HTML runs in a sandboxed frame. Without allow-same-origin, the frame gets an opaque origin: it has no cookie, no storage, and no access to the host page. A content security policy with connect-src 'none' means it cannot call the API, reach the internet or open a socket.

Provenance — did this request come from my app?

SameSite answers “is this another site?”. It does not answer “is this my app?”. Behind one domain, sibling subdomains are the same site, so a compromised app on one subdomain can POST to another with the user’s cookies attached.

The missing control is a server-side Origin check on every state-changing route, plus __Host- cookie names and no Domain attribute, so cookies stay host-only.

The layers do not compensate for each other. TLS without Secure still lets the cookie out over a plain request. SameSite without an Origin check leaves you open to a sibling app. A perfect sandbox does not help if the server trusts a user id from the request.

05

One request, end to end

Here is what happens when a user opens a screen and reads a number. The point is not the sequence; it is where each decision is made.

  1. The browser sends a request with the cookie the server gave it earlier. It is a claim, not an identity.
  2. The proxy terminates TLS and forwards the request. It also redirects HTTP and sends HSTS on the way back. It does not authenticate users.
  3. The app looks up the session. A known id becomes a user; an unknown one becomes “not signed in”. The username is never taken from the request body.
  4. The app checks access to this screen against the user’s TM1 groups.
  5. The app connects to TM1 as that user — one TM1 session per user, not a shared login.
  6. TM1 evaluates the query under that user’s security. It decides what rows and cells exist in the answer.
  7. A write takes the same path, plus: the app re-reads the saved screen to know which cubes it may write, rejects calculated cells, and refuses a value that changed since the screen loaded.
  8. A process run takes the same path, plus: the app checks the process is declared by the saved screen and the parameters match its own.

The page decides nothing. It may send questions — an MDX query, a coordinate, a number — and the server answers them as the signed-in user.

06

What the server must never accept

Never accepted from the pageWhere it comes from instead
a user id, username or “current user”the session behind the cookie
a server, environment or tenantconfiguration on the app
a permission, role or “canWrite” flagTM1, on the request
which cubes or processes may be usedthe saved screen, which is a recorded model change
an access token or TM1 sessionthe app’s own memory, per user

The last row is what makes write-back trustworthy even when the page is untrusted: the app does not believe the running page about what it may write. It re-reads the saved document, which was reviewed and deployed like any other model object. A page cannot widen its own permissions by editing its HTML.

07

Three failures worth recognising

1. The Secure flag that follows a boolean

The app asks “does this process serve TLS?” A proxy answers for it in production, so the process says no and the cookie is written without Secure. The site is HTTPS; the cookie is not protected.

2. SameSite=Strict and no Origin check

It blocks evil.com, so it feels finished. But a second app on a sibling subdomain is the same site, and a script there can POST to your API with the user’s cookie.

3. One wildcard, many apps

Convenient: one certificate, one proxy, one route per app. But cookies are host-only while SameSite sees one site, so the apps are isolated for storage and grouped for requests.

Cookie scopeSameSiteCORS
lens.corp.example.comown jarsame siteown origin
ide.corp.example.comown jarsame siteown origin

That is fine for apps at the same trust level, and wrong for apps that must not trust each other. If you need isolation, use separate registrable domains, or an Origin check plus strict CORS between siblings.

08

The checklist

Before anything reaches a user:

  1. A certificate from a CA the users’ machines already trust. Their internal CA is normal for an internal app; a public CA for anything reachable outside.
  2. A reverse proxy terminating TLS, with apps bound to loopback. Nothing should reach the app over plain HTTP except the proxy.
  3. HTTP redirected to HTTPS, and HSTS sent. Otherwise the first request, including the password, can be plain.
  4. Secure derived from the request, not a configuration switch. Trust the proxy and read the external scheme.
  5. A __Host- session cookie, with a distinct name per app. Host-only, Path=/, Secure; no Domain.
  6. Origin checked on every write, process run and preference change. SameSite is not a substitute.
  7. An idle timeout and an absolute maximum session age; sign-out revokes the server-side session. Deleting the cookie alone leaves it usable.
  8. The back hop to TM1 verified. Never disable certificate verification to make an internal certificate “work”; install the right root instead.
09

Five tests you can run

You do not need to be a web developer to prove the important parts. These take ten minutes with a browser and a terminal.

1. Read the cookie flags

Sign in, then open DevTools → Application → Cookies. The session cookie should show HttpOnly, Secure, SameSite=Strict, and a path of /. If Secure is missing on an HTTPS site, the flag is following the wrong thing.

2. Call the API without the cookie, then with it

curl -i https://lens.example.com/api/lens/lenses
curl -i -H 'Cookie: lens_session=<value>' https://lens.example.com/api/lens/lenses

The first should be 401. The second should be 200. If the first succeeds, something is not checking the session.

3. Sign out, then replay the old cookie

Copy the cookie value, sign out, and repeat the second call. It must be 401. If it still works, sign-out cleared the browser but not the server.

4. Try to escape the frame

Open the frame URL directly, then in its console try document.cookie, localStorage, and fetch('/api/lens/lenses'). All three should fail or be empty. The network request should never appear in the Network tab — connect-src 'none' stops it before it is sent.

5. Sign in as two users

Use two browser profiles. Each should see only their own slice of the model. Then ask TM1 to read a member the other user cannot see: it must be refused, not filtered by the page.

The point of the tests is the refusal. A check that cannot fail is worse than no check; prove the system says no when it should.

Questions for a client’s security team

These turn a review into a conversation, and they are the questions that decide the deployment shape.

QuestionWhy it matters
Which CA signs the existing platform, and do all user devices trust it?decides whether internal certificates work without warnings
Can you issue certificates for these internal hostnames?avoids self-signed certificates and user warnings
Is there an existing reverse proxy, and who owns it?sets where TLS terminates, and who can see cookies
Are all users on managed devices?unmanaged phones and laptops will not trust an internal CA
What is the session timeout policy — idle, absolute, or both?the app must match the policy, not invent one
Is the app internal-only, or reachable from outside?decides internal CA vs public CA
Who may author screens, and who reviews them before release?authored HTML is a trusted input; review is a control
What access and activity logging is required, and for how long?drives what the app records and how long it keeps it

A short glossary

TermIn one sentence
Originscheme + hostname + port; the unit the browser uses for “may this page read that?”
Sitethe registrable domain (corp.example.com); ports and subdomains do not count. Used by SameSite.
CSPa header listing what a page may load and connect to. It can stop a request before it is made.
CORSa header allowing another origin to read a response. It controls reading, not sending.
CSRFmaking the user’s browser send a state-changing request to a site it is signed in to. SameSite is the main defence.
XSSgetting your JavaScript to run inside someone else’s page. HttpOnly stops it reading the cookie, not acting as the user.
Opaque origina sandboxed frame’s identity: it has no cookie, storage or access to the parent.
HSTSa header telling the browser to use HTTPS for this host from now on, before the request is made.
Bearer tokena credential where possession is enough. A session cookie is one.
CA / internal CAthe authority that signs certificates. A company CA is trusted on its managed machines by policy.
SNIhow the browser tells the server which hostname it wants, so one proxy can hold many certificates.

How this was tested. The controls described here are the ones implemented in the Lens runtime in this repository, and they are covered by its test suites: sign-in and session flags, idle timeout, per-user identity, a sandboxed frame with its own CSP, group access on every route, declared write cubes and processes, and the server always taking its target from configuration. Not yet proven: an independent penetration test, and a production deployment behind a real internal CA and proxy. Those are the next two gates, not claims in this article.

Still open

  • An Origin check on writes. Today SameSite=Strict is the CSRF control; it does not cover sibling apps on one domain.
  • An absolute session age. The runtime has an idle timeout; it needs a maximum too.
  • __Host- cookie names. A rename, and a sign-out for everyone — best done before a pilot.
  • PAW single sign-on. The runtime signs in with TM1 credentials today; trusting a PAW session is a separate integration.
  • Load and session-leak testing with several users and a real TM1 server.

TLS protects the channel. Identity and authorisation protect the data. Isolation protects the app from its own content. Provenance protects one app from another. None of them compensates for the others being missing.

AI can write the screen. Only the architecture makes it safe.
